# 读陌生代码的方法论

> 从一次读 Karpathy nanoGPT 反复卡壳的复盘中沉淀。
> 不针对任何具体代码,只讲方法。

---

## 0. 一句话总病根

**自底向上猜测**:从陌生函数的函数体一行一行往下看,试图反推它在干嘛。

这是错的。读代码必须**自顶向下定位**。函数体是最后一步,不是第一步。

---

## 1. 三层理解栈

任何一段代码都同时存在三层:

```
[ 领域层 ]  这个代码在解决什么问题?     ← 不在代码里,在问题定义里
[ 算法层 ]  抽象上用什么思路解的?       ← 不在代码里,在论文/范式里
[ 实现层 ]  代码具体怎么写的?           ← 在代码里
```

**读不懂实现层,99% 是因为上两层是空的。**

实现层的信息无法反推上两层。试图反推就是自找痛苦。这就是为什么"逐行读注释"经常没用——注释只能补足实现层,补不了上两层的空白。

**对策**:遇到陌生代码,先花 5 分钟搞清楚领域层和算法层,**然后才**打开代码。这 5 分钟会节省你几小时的挣扎。

---

## 2. 形状 ≠ 含义

知道一个张量是 `(4, 23)`,不代表你理解它。
知道一个变量是 `dict`,不代表你理解它。

**形状是语法,含义是语义。**

`(4, 23)` 里的 4 为什么是 4?这是领域知识决定的,不在代码里。**只在你脑子里有领域模型时,形状才有意义**。

**对策**:遇到不理解的张量/数据结构,不要继续往下读代码。**回到上层去找"这个 4 代表什么"**。这个答案永远在领域定义里,不在更深的代码里。

---

## 3. 含义不在代码里,在数据里

```
代码    = 操作数据的工具
数据    = 真相本身
```

想知道一段处理函数干了什么,**第一步永远是看它处理的原始数据长啥样**,不是读处理逻辑。

数据文件(JSON / CSV / .npy / 数据集样本)是 ground truth。读取/处理数据的函数只是工具。**绕开工具直接看数据,永远是最快的**。

**对策**:遇到"这个函数干嘛"的疑问,先问"它的输入数据原始长啥样"。打开数据文件直接看一眼,比读代码快 10 倍。

---

## 4. 自顶向下读法(取代自底向上)

正确的读代码顺序:

```
1. 找调用点  (谁在用这个函数?调用上下文是什么?)
2. 看返回值怎么被使用  (返回的东西去哪儿了?用来干嘛?)
3. 看输入参数实际长啥样  (sandbox 里 print 一下)
4. 这个函数在 pipeline 哪一步?  (数据加载?训练?评测?)
5. 最后,才读函数体
```

前 4 步通常 1-2 分钟搞定。**做完前 4 步,函数体往往不读自明**。

**反模式**:跳过前 4 步直接啃函数体。注定要靠猜。

---

## 5. 沙盒原则

想测试/观察一段代码时,**不要复制代码**。

```
❌ 把函数复制到新文件 → 发现它依赖别的函数 → 也得复制 → 递归地狱
✅ 在原文件旁边建一个"新入口",从外面调用它 → 依赖自动满足
```

**沙盒 = 新入口,不是新文件。**

新入口的形式:
- 同目录下新建文件,`from xxx import yyy` 调用
- 原文件底部加 `if __name__ == "__main__":` 块
- Jupyter notebook,import 后直接调用
- Python 交互式窗口

**心法**:代码留在原处,你从外面戳它,观察反应。复制代码 ≠ 沙盒。

---

## 6. 黑盒契约原则

读代码遇到一个函数调用 `foo(x)` 时,**默认把它当黑盒**:

```
契约清楚(知道返回啥、形状啥样) → 假装它是黑盒,继续往下读
契约不清楚                     → 先看契约(print / 看 return / 看 docstring),仍然不深入
真正需要细节                   → 才打开函数体
```

**永远不要为了搞懂一个函数把所有它调用的函数都展开**。这会无限递归,把你拖垮。

**95% 的函数应该是黑盒**。专业开发者读陌生代码就是这么读的。

什么时候才能"停在契约层"?
- 调用者只关心结果,不关心过程 → 停
- 函数名/参数名已经表达了意图 → 停
- 你怀疑这里有 bug 或关键逻辑 → 不停,展开

## 7. 范式问题 vs 实现问题

**两种本质不同的问题需要不同解法**:

| 问题类型 | 典型问法 | 在哪找答案 |
|---------|---------|----------|
| 实现问题 | "这行代码做了什么操作" | 看代码 / 查文档 |
| 实现问题 | "这个张量形状是啥" | print |
| 实现问题 | "这个函数返回啥" | 看 caller / print |
| **范式问题** | **"为什么这样能解决问题"** | **论文 / 教程 / 问 AI** |
| **范式问题** | **"这种模型怎么做到 X 的"** | **论文 / 教程 / 问 AI** |

**范式问题 100% 不在代码里**。代码只是某个范式的一种实现。试图从代码反推范式 = 缘木求鱼。

**识别信号**:问题里出现"为什么"、"怎么做到"、"什么原理"——立刻停止读代码,去外部找答案。

---

## 8. 环境信任度问题

改了代码看不到效果时,**第一反应不要怀疑代码,先怀疑环境**:

```
我看到的代码 ≠ 实际跑的代码

可能的 gap:
- 文件没保存
- 改的不是被实际加载的那个文件(同名文件、路径误会)
- 改的不是被实际调用的那个函数(同名函数、重复定义)
- 运行时缓存了旧版本(notebook / REPL 的模块缓存)
- 静态查看工具读文件、运行时跑内存,两者不一致
```

**心法**:当"我看到的"和"实际行为"对不上时,默认是环境层面的同步问题,而不是代码逻辑问题。

---

## 9. 允许自己"暂时不懂"

读陌生大型代码,**第一遍跳过 helper 函数是合理的**。

你只需要知道某个 helper "返回什么类型的东西",就能继续读主流程。等主流程懂了,**再回头看 helper,通常 5 分钟就懂**——因为那时你脑子里有上下文了。

**反模式**:坚持把第一个不懂的地方钻穿才往下读。这会让你卡在前 10% 的代码里,永远到不了主干。

主干 → 分支 → 叶子。这个顺序不能反。

---

## 10. 一份速查 Checklist

每次卡住时,按顺序问自己:

```
[1] 我卡的是"实现"还是"范式"?
    → 范式:出去找资料,别在代码里挣扎
    → 实现:继续往下

[2] 这个代码处理的数据原始长啥样?
    → 不知道:先打开数据文件看一眼
    → 知道:继续往下

[3] 这个函数的 caller 在哪?它怎么用返回值?
    → 不知道:Grep 函数名,看一眼调用现场
    → 知道:继续往下

[4] 这个函数的输入输出实际是什么样?
    → 不知道:在沙盒里 print 一下
    → 知道:继续往下

[5] 现在再读函数体
    → 此时通常已经懂了
    → 还不懂:可能是某个被调用的子函数契约不清,定向打开它的契约层

[6] 如果改了代码效果对不上:
    → 文件保存了吗?
    → 实际加载的是这个文件吗?
    → 运行时是不是缓存了旧版本?
```

---

## 11. 心法总结(三句话)

1. **代码不包含它自己的意义。意义在问题里、在数据里、在范式里。**
2. **读代码 = 在合适的抽象层停下来,不是理解所有细节。**
3. **看到的 ≠ 跑的。改了没生效,先怀疑环境。**

---

## 12. 反模式对照表

| 反模式 | 正确做法 |
|--------|---------|
| 从函数体开始读 | 从调用点开始定位 |
| 脑子里推张量形状 | print 一下 |
| 把代码复制到新文件测试 | 新入口 import 调用 |
| 为搞懂 A 把它调用的 B C D 都读完 | A 调用的函数默认黑盒 |
| 试图从代码反推"为什么这样能解决问题" | 出去看论文/问 AI |
| 读处理数据的代码来理解数据格式 | 直接打开数据文件看 |
| 第一遍读就要懂每一行 | 第一遍读主干,helper 当黑盒 |
| 改了没生效就反复检查代码逻辑 | 先检查环境(保存/加载/缓存) |

---

## 最后

读代码读不懂时,**最容易的反应是"再读一遍"**。
最有效的反应是**"换个动作"**——找调用点、打印数据、查范式、跳过这段。

**"再读一遍"很少能突破卡点**,因为卡点的根源往往不在这段代码本身。
